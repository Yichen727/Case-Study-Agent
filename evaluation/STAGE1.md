# 阶段 1：来源、身份与数据库迁移

完成日期：2026-10-28。自动检查完成，等待用户手工复测。本阶段新增数据基础与必要的界面展示，未推进阶段 2 的非标准解析或阶段 3 的后台任务。

## 实际变化

- 每次显式导入生成独立 `source_id`，Case ID 为 `source_id:original_slide_id`。页码和文件名都是显示信息，不再决定全局身份。
- 不同 PPTX 即使同名、相同页码、相同原始 Slide ID，也不会覆盖。每页独立；同名或延续页不合并。
- 在数据库旁的 `uploads/` 保存按 UUID 命名的不可变快照，边复制边计算 SHA-256，只解析保存后的快照。解析或入库失败时清理该次快照。
- 来源和整批案例使用短事务提交；SQLite 写入串行提交，解析不持有写锁。并发初始化会在锁内复查 schema 版本。
- 新增字段当前来源及验证记录，保留修改历史。再次保存同一个导入结果只补首次写入，保留人工修改；重新上传则视为新导入，不复制另一来源的人工值。
- 新导入和人工修改后都为 `NEEDS_REVIEW`，字段齐全或字段标记 confirmed 不会自动批准整个案例。显式 Approve 留到阶段 4。
- 界面可多选 PPTX，一次提交后逐文件处理。结果、案例表和元数据选择器展示来源文件与页码；原始 Slide ID 与数据库内部 slide_id 分开，均不展示给普通用户。
- 页面共用一次案例列表读取；字段来源面板仅读取当前所选案例。网页补充仍在导入中同步运行。初始化缓存已在下述问题修正中移除。

覆盖：

- 不同文件名 / 相同文件名，分别执行顺序 / 两线程并发导入：两份文件总计 3 页，均保存 3 条独立案例。
- 两份文件第 1 页的原始 Slide ID 相同，Source ID 与 Case ID 不同。

- 无效文件或写入中途失败时，无半批来源 / 案例，快照得到清理。
- 旧库迁移前备份，正文与修改历史保留，迁移只执行一次；备份或迁移失败时回滚旧 schema。

## 实际数据库迁移

已将 `data/case_studies.sqlite3` 从 schema 0 迁移为 schema 1，迁移前备份：

```text
data/backups/case_studies.before-v1-83b807b6.sqlite3
```

结果见 [stage1_migration.json](stage1_migration.json)：原有 **60 条案例、60 条幻灯片正文全部保留**；原库无修改历史记录，数量保持 0；数据库完整性与外键检查通过。

旧记录按旧文件名建立一个“历史来源”分组，仅供追踪旧数据，不表示已经找回原件。其原始 Slide ID、快照与内容哈希不做猜测，字段来源标为 `LEGACY_UNVERIFIED`，UI 显示 `Re-import required`。旧 `confirmed` 统一转为 `NEEDS_REVIEW`；已有显式 approved 值保留为 APPROVED。

旧记录不会与后来重新上传的案例自动合并；重新上传会新增一组带快照和独立来源的记录。若以前已经发生覆盖，需要从原 PPTX 重导入恢复，迁移本身无法还原已丢失的数据。

迁移采用事务，失败会保留旧库。需要人工恢复备份时先停止应用并另外保留当前数据库；备份的 schema 为旧版，新版应用再次启动仍会执行迁移。

原始值见 [baseline_stage1.json](baseline_stage1.json)。使用同一份 83 页、约 321 MiB 公司文件，临时数据库，网页补充模拟为不可用：

| 每次页面重运行完整列表读取 | 3 次 | 1 次 |
| 页面重运行 init_db 调用 | 1 次 | 0 次 |

导入总计增加了快照复制、哈希及字段来源写入；解析基本不变。上述 UI 值只反映服务端执行，不含浏览器绘制、上传及在线网页等待，且样本量小，不能据此承诺最终延迟。

上表是阶段 1 初版的历史测量。后续为修复空库问题移除了初始化缓存，现在每次页面执行会调用一次轻量版本检查，已是当前版本时立即返回，不重复建表或迁移；表中 0 次 init_db 不再描述当前实现。

公司文件仍识别出 60 张案例页，样本集合未改变。第 19–21、23–25 页标题和第 80 页章节问题仍留在阶段 2，原始样本 SHA-256 与阶段 0 一致。

## 用户手工复测步骤

1. 停止旧的 Streamlit 进程，在项目根目录用原来的 Python 环境运行 `python run.py`。
2. 打开 All cases，记下当前总数。当前已迁移旧库为 60 条；旧记录出现 `Re-import required` 属于预期。
3. 在上传控件中同时选中 [source_a.pptx](fixtures/source_a.pptx) 与 [source_b.pptx](fixtures/source_b.pptx)，点击 **Parse and save decks**。本批应增加 **3 条**：source_a 两条，source_b 一条。
4. 在 All cases 中核对：三个标题均为 `SYNTHETIC: SAME NAME`；Source deck 后紧跟 Slides，分别能看到 source_a 的第 1、2 页和 source_b 的第 1 页。表格隐藏 Source ID、Case ID、Original Slide ID 和 Snapshot 栏。
5. 搜索 `SYNTHETIC: SAME NAME`，首次导入这组样本时应显示 3 条，包含两个第 1 页和一个第 2 页。
6. 在 Complete metadata 选择 source_a 的第 1 页，将 Client 保存为 `Only source A`。再核对 source_b 的第 1 页和 source_a 的第 2 页，Client 应维持原值；Field sources and verification 中能看到修改来源。
7. 可再试同名文件：将两份样本放在不同文件夹并改为相同文件名，分别上传。新增记录在数据层仍有不同 Source ID；完全同名同页的下拉选项用 copy 序号区分，选择和编辑不会串到另一条。

每次再次点击导入都会建立新来源。因此复测多轮时按“本批增加 3 条”核对，搜索总数可能大于 3。当前导出仍为占位入口，本阶段无需测试 PPTX 导出。

## 用户复测后的问题修正（2026-10-28）

- 已复现初始化缓存仍在、数据库文件被删除或替换为空文件时的 `no such table: cases`。移除页面初始化缓存，初始化函数返回是否实际建库 / 迁移；发生重建时同时清理旧搜索与选择状态。
- 回归覆盖缺失数据库、空文件首次启动，以及同一进程中初始化后删除 / 重建数据库，均正常显示空案例库。
- 成功提示去掉 Import ID；All cases 和搜索卡片隐藏内部 ID，Slides 紧跟来源；选择器和字段证据面板也隐藏内部标识。
- 同名同页标签用 copy 序号区分，验证两张案例仍可独立选择和编辑。全部 22 项测试通过。

后续确认的完整性状态与搜索操作已落实：

- 表格与搜索卡片使用同一完整性规则；七个核心字段齐全显示 Confirmed，缺失显示 Needs Review。人工 Approved 和逐字段验证记录保持独立。
- 在人工补齐最后一个字段后，表格和再次检索的卡片均显示 Confirmed；清空该字段后恢复 Needs Review。既有记录无需重新导入。
